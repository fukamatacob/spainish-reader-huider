Ты инженер, выполняющий один ограниченный технический эксперимент в репозитории fukamatacob/spainish-reader-huider. Прочитай SPEC.md, docs/POC_PLAN.md, docs/TECHNICAL_AUDIT.md и при необходимости docs/DESIGN_SYSTEM.md. Следуй актуальной SPEC, не историческим UX-решениям донора. Не реализуй весь продукт. Проверь git status, сохрани чужую работу, используй отдельную ветку/worktree либо уже выделенную рабочую ветку. Не пушь и не сливай main без явного указания. Не используй destructive reset. Не публикуй секреты, личные данные, большие базы/модели/APK и нелицензированные исходные данные. Для существенных загрузок/установок проверь объём и разрешение. Не запрашивай ключи в чат/логи; используй только разрешённый локальный секрет. Не выдавай результаты mock/эмулятора/предположения за live/device. При блокере выполняй независимые части, укажи точную причину и команду для продолжения.
В своей директории создай README.md, REPORT.md, код, тесты, небольшие results/ с сырыми метриками и разрешёнными fixtures. Запиши версии, SHA, лицензии, команды, exit codes, окружение, что реально проверено, отклонения и воспроизведение. В конце: PASS/PARTIAL/FAIL/BLOCKED, ADOPT/ADAPT/REJECT/NEEDS MORE EVIDENCE, перечень изменённых файлов и конкретный следующий шаг. Не отмечай эксперимент завершённым без критериев из POC_PLAN.md.

Рабочая директория: experiments/02-dictionary/. Цель: получить воспроизводимую индексированную базу и SQLite-only baseline, пригодный для сравнения с NLP.

1. Проверь доступные снимки https://kaikki.org/dictionary/Spanish/index.html и https://github.com/doozan/spanish_data. Зафиксируй точные URL/commit/даты/SHA256, форматы и лицензии каждого набора и производных данных. Не распространяй базы до проверки прав. Если загрузка крупная, сначала размер/место и разрешение. Начни с маленького законного fixture и затем полной сборки, если разрешено. Не делай вывод о покрытии полной базы по маленькому fixture.
2. Реализуй потоковый Python ETL на Mac (без Python в Android): Unicode NFC, нормализация регистра с сохранением ñ/ударений, исходных форм и provenance. Раздельные lexemes, senses, forms с many-to-many, expressions, examples, frequency или эквивалентная проверяемая модель. Не сливай омонимы, не выдумывай смысл/морфологию. Добавь индексы и manifest; не зависеть от rowid разных версий. Данные raw/output локально в ignored cache.
3. Реализуй детерминированный lookup кандидатов по словоформе и baseline ranking без NLP; задокументируй tie/unknown. Покажи, что vino имеет несколько кандидатов; проверь dímelo, hicieron, tenés, darse cuenta de, guagua, banco и диакритику. Тесты нормализации, constraints, integrity_check, EXPLAIN QUERY PLAN. Считай отдельно уникальные леммы, словоформы и записи значений, не смешивай.
4. Подготовь размеченный корпус v0 200–500 токенов по правилам POC_PLAN.md, реальный и challenge отдельно, holdout по документам. Если человеческой проверки нет — пометь provisional, не выдумывай проверку. Сохрани разрешённые fixtures и схему gold. Не используй результаты будущего движка для разметки.
5. Измерь покрытие правильных кандидатов, baseline top-1 lemma/POS, неизвестные и ошибки. Профилируй размер DB, сборку, RAM и cold/warm p50/p95 поиска на Mac и Android ARM64 отдельно; минимум 100 warm запросов с описанием выборки. Android harness read-only, airplane mode. Если телефона нет, дай воспроизведение и BLOCKED DEVICE.

Критерии: ETL и lookup повторяемы; исходная форма и неоднозначность сохранены; manifest, тесты, raw metrics и baseline predictions для 03. Ориентиры ≥95% candidate coverage, p95 warm lookup ≤50 ms на устройстве; не считать достигнутыми без замера. Отклонения объяснить. Не сокращай базу произвольным числом слов и не выбирай окончательный NLP.

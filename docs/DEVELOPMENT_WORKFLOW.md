# Регламент мультиагентной разработки

Версия 1.0 · 27 ноября 2026 г.  
Статус: согласованный процесс разработки Spanish Reader, не новая продуктовая спецификация.

## 1. Общая память и роли

Один репозиторий: https://github.com/fukamatacob/spainish-reader-huider. Git — источник проверяемого состояния; GitHub хранит опубликованные коммиты, а локальные незапушенные изменения видны только в соответствующем окружении. Чаты, внутренние журналы harness, скрытые рассуждения, память моделей и история терминала не являются обязательным контекстом проекта.

- Владелец утверждает требования, расходы, доступы, существенные архитектурные изменения и слияние результатов.
- ChatGPT — технический руководитель: декомпозиция, оценка рисков, проверка доказательств, подготовка следующего задания, обновление согласованных документов. Не имеет прямого доступа к локальному Mac без отдельного инструмента.
- OpenCode + DeepSeek — основной исполнитель рутинных и хорошо ограниченных задач.
- Codex — сложные задачи, независимое ревью и эскалация.
- Claude Code — альтернативный исполнитель/ревьюер. Смена harness при сохранении той же модели не гарантирует независимой оценки качества.

Распределение — рабочая гипотеза, не сравнительный бенчмарк моделей. Выбор зависит от фактического результата, доступности, лимитов и инструментов. Не добавлять отдельный оркестратор, MCP-сервер или платную подписку только ради этого процесса.

Не дублировать полную SPEC в AGENTS.md или в каждом задании. Ссылаться на разделы и точный базовый commit. Старые отчёты остаются историческими. При противоречии утверждённые требования определяют цель, исходный код и тесты — фактическое состояние; расхождение явно фиксировать, не исправлять требования молча. Общее состояние обновляет один координатор, чтобы параллельные агенты не перезаписывали его.

## 4. Параллельная работа и Git

PoC 01 и 02 могут выполняться независимо (02 сначала на Mac); 03 требует данных/корпуса/baseline от 02. 04 и 05 используют проверенное Android-окружение 01 и независимы от реального NLP: Reader на stub, интеграции по отдельности. 03/04/05 могут пересекаться по SDK, NDK, кешам, эмулятору и физическому телефону: установки инструментов и device-бенчмарки сериализовать. Не одновременно менять общий Gradle root или shared interfaces. PoC-контракты предварительные, финальные интерфейсы Alpha согласовать после gate.

Один агент = одна изменяемая ветка и рабочая директория. Git worktree предпочтителен для нескольких локальных исполнителей. Существующий клон и активную ветку не перестраивать во время работы. Новый worktree создаётся от проверенного SHA, не от предположения о свежести main. Имена веток: poc/01-donor-build, poc/02-dictionary и т. п.; после PoC task/<id>-<slug>. Если ветка уже существует, проверить её статус, не удалять и не пересоздавать. Команды выполняет агент, не пользователь. Пример только после проверки путей и отсутствия такой ветки:

    git status --short --branch
    git fetch origin
    git worktree list
    git worktree add -b poc/04-reader ../reader-poc04 origin/main

Для двух агентов не использовать один рабочий каталог даже при разных моделях. Не менять файлы другого worktree, не переключать ветку под активным агентом. Изоляция файлов не изолирует CPU/память/порты/SDK, поэтому координировать ресурсы Mac. Путь/команда в примере условные.

Передача между локальными harness возможна по тому же worktree после остановки предыдущего автора или в новом worktree от его коммита. Облачный Codex не видит локальные коммиты/игнорируемые данные: передача через разрешённую опубликованную ветку или явно предоставленный артефакт с manifest. Не пушить автоматически. Секреты, приватные тексты, APK, большие базы и модели остаются локально, передаются только разрешённым способом; восстановление через загрузчики и контрольные суммы. Если лицензия запрещает публикацию данных — не загружать их даже в ветку.

## 5. Жизненный цикл задания

1. Координатор даёт задание: ID, цель, base SHA, зависимости, scope/не scope, критерии, тесты, лимит расходов, право на установку/доступ/публикацию. Для PoC использовать имеющиеся prompts, для новой задачи — templates/TASK.md.
2. Исполнитель проверяет git status, базовый SHA, документы и доступность инструментов; сообщает конкретный блокер, если есть. Не останавливать независимые проверки без причины.
3. Реализация и тесты в своей ветке. Коммитить небольшие логически связанные изменения; не включать чужие незакоммиченные файлы. Сохранять воспроизводимость и негативные результаты.
4. На контрольной точке — отчёт, checkpoint commit (локальный, если push не разрешён), diff, команды, exit codes, данные и ограничения. Если checkpoint невозможен, handoff содержит незакоммиченный diff и точный способ восстановления, а не только SHA.
5. Ревьюер получает конкретный commit/range, задачу и доказательства. Сначала читает код и воспроизводит критичные проверки, потом сравнивает с заключением исполнителя; review может быть read-only. Исправления — отдельная явно назначенная задача.
6. Руководитель сверяет критерии, проверяет интеграционные тесты на объединённой версии и предлагает решение владельцу. Только после одобрения — слияние и обновление PROJECT_STATE/TECHNICAL_DECISIONS. Не использовать force push, destructive reset или автоматическое разрешение конфликтов без проверки.

Статусы задания: NOT STARTED / IN PROGRESS / BLOCKED / READY FOR REVIEW / CHANGES REQUESTED / ACCEPTED. Статус эксперимента (PASS/PARTIAL/FAIL/BLOCKED) отдельно от статуса задания и отдельно от решения ADOPT/ADAPT/REJECT/NEEDS MORE EVIDENCE. ACCEPTED не значит, что все функции продукта готовы.

## 6. Передача и эскалация

После двух содержательных попыток без измеримого прогресса — пауза, HANDOFF.md по шаблону, независимый анализ другой моделью. Две попытки — стартовое правило, не повод прерывать работающую сборку. Содержательная попытка: новая проверяемая гипотеза, команда и результат. Немедленная эскалация при повторении одних действий, попытке удалить тесты/ослабить критерии, менять архитектуру ради обхода, рисках секретов/потери данных или превышении согласованного бюджета. Не эскалировать простую установку или известную недостающую зависимость без проверки.

При передаче: остановить автора, зафиксировать состояние, ветку, SHA, dirty status и diff, точные команды, блокирующую ошибку, гипотезы, отвергнутые попытки, что не проверено. Новый агент сам воспроизводит ошибку и не обязан соглашаться с диагнозом. Не переносить весь чат. Если контекстное окно близко к пределу, сохранить handoff до смены сессии даже при той же модели.

Безопасность, миграции, идентичность лексем, конкурирующие операции, лицензии и ключевые контракты — отдельное независимое ревью перед интеграцией. Не считать ревью другой сессией той же модели гарантированно независимым.

## 7. Практика запуска

На текущем этапе не прерывать PoC 01, не запускать дубликат и не требовать немедленного pull в активной ветке. После checkpoint безопасно получить новые инструкции из origin/main (fetch; затем осознанное обновление/merge либо новый worktree), не теряя локальные изменения. Владелец пересылает ответы агентов и утверждает действия, требующие полномочий; все технические команды выполняют агенты. Нет автоматического управления локальным OpenCode со стороны ChatGPT.

Для нового агента достаточно: «Прочитай AGENTS.md, docs/PROJECT_STATE.md, задание <path>. Работай в <worktree/branch> от <SHA>, сначала проверь состояние. Выполни только указанную задачу и подготовь отчёт. Не пушь/не сливай без разрешения». Для ревью — точный SHA и шаблон REVIEW.md. Для смены исполнителя — HANDOFF.md, точная ветка и commit.
